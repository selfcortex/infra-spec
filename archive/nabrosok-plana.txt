# Архитектура RAG-репозитория

## Состав: 3 контейнера

| Сервис | Что это | Почему так |
| :--- | :--- | :--- |
| `embedder` | второй `llama-server` с `--embeddings`, **на CPU** | VRAM у тебя забита (~15.0 из 16 ГБ в headless), даже 0.6B-модель на GPU съест контекст основной модели. Запрос на эмбеддинг короткий, CPU справляется |
| `qdrant` | векторная БД | один бинарник, свой volume, фильтры по payload и гибридный поиск есть из коробки |
| `rag-core` | один Python-процесс (FastAPI + MCP SDK + qdrant-client) | и MCP, и OpenAI-прокси, и ингест в одном месте, без отдельных сервисов |

Caddy, Redis, брокеры, отдельный reranker и прочее не нужны. Единственное место, где можно сократить до 2 контейнеров, это встроенная БД (sqlite-vec или LanceDB прямо в `rag-core`). Для личного масштаба этого хватит. Но Qdrant я бы оставил: индекс переживает пересборку ядра, и фильтры с гибридом уже готовы.

## Схема связей

```
Chatbox ──(OpenAI API)──────┐
                            ▼
opencode ──(MCP)───────► rag-core :8090 ──► embedder :8081 (CPU)
   │                        │   └─────────► qdrant :6333
   │                        └─(/v1 прокси)─► llama-server :8080 (GPU, старый репо)
   └──(LLM напрямую)────────────────────────────────┘
```

Opencode ходит в **два** места: за знаниями в `rag-core` по MCP, а за генерацией напрямую в `llama-server`. Через ядро его LLM-трафик гнать незачем. Chatbox знает только `rag-core`, а тот сам решает, прокинуть запрос как есть или обогатить.

## Сети

| Сеть | Тип | Кто внутри |
| :--- | :--- | :--- |
| `ai-net` | **external** bridge, создаётся один раз (`docker network create ai-net`) | `llama-server` (из старого репо), `rag-core`, опционально `prometheus` |
| `rag-net` | bridge с `internal: true` | `rag-core`, `embedder`, `qdrant` |

- `internal: true` отрезает embedder и qdrant от интернета и от хоста. Модели монтируем с диска, как в старом README, скачивать им нечего.
- `rag-core` сидит в обеих сетях. Из `rag-net` он видит БД и эмбеддер, из `ai-net` видит LLM.
- Через `ai-net` старый и новый репозитории общаются без общего compose-файла. В старом репо меняется минимум: у `llama-server` добавляется вторая сеть с алиасом `llama`. `rag-core` ходит на `http://llama:8080`.
- Ходить через `host-gateway` на опубликованный порт не получится: он у тебя привязан к `127.0.0.1` и `LAN_IP`, из контейнера туда не попасть.

## Порты

| Порт | Сервис | Публикация |
| :--- | :--- | :--- |
| 8080 | llama-server (LLM) | как сейчас: loopback + LAN_IP |
| **8090** | **rag-core** | **loopback (opencode) + LAN_IP (Chatbox)**, по тому же шаблону |
| 8081 | embedder | не публикуется |
| 6333 | qdrant | не публикуется (6334/gRPC не нужен) |
| 3000 | grafana | как сейчас |

На 8090 пути разделены: `/mcp` для opencode, `/v1/*` для Chatbox, `/ingest` и `/health`, `/metrics` служебные. Порт один, ключ один.

## Ключи

Тот же подход, что в старом репо (`secrets/`, файлы):
- `rag_api_key` нужен клиентам (opencode, Chatbox) для входа в `rag-core`.
- `llama_api_key` нужен `rag-core`, чтобы ходить в LLM (ключ тот же, что в старом репо, монтируется read-only).
- Qdrant на внутренней сети тоже закрываем ключом: это одна строка в конфиге.

TLS пока не нужен: в README у тебя та же логика доверенной LAN. Если понадобится, ставится один прокси перед 8090 и больше ничего не меняется.

## Потоки данных

1. **Ингест:** файл → `rag-core` (парсинг и чанкинг) → `embedder` батчами → `qdrant`. Id точки = хеш пути и чанка, поэтому переиндексация инкрементальная. **Ингест работает без GPU-сессии**, пока модель вообще не запущена.
2. **MCP-поиск (opencode):** агент вызывает `search(query, collection, k)` → эмбеддинг → top-k из Qdrant → чанки с источником и score. LLM ядро не трогает, решает агент. Инструменты: `search`, `list_collections`, `get_document`.
3. **Chatbox:** ядро показывает **две виртуальные модели**: `qwen3.8-27b` (чистый passthrough) и `qwen3.8-27b+rag` (с подмешиванием контекста). Так RAG включается переключателем модели, а не навязывается каждому запросу. Для RAG-модели: последний вопрос → эмбеддинг → Qdrant → system-сообщение с пронумерованными источниками → llama-server → стрим назад. Passthrough отдаёт SSE без изменений, включая `reasoning_content`.

## Что нужно зафиксировать до yml

- **Бюджет контекста.** У тебя 80k, из них под инжект стоит отдать примерно 4–6k токенов (top-k 5–8 чанков по ~512). Это параметр ядра, а не магия.
- **Модель эмбеддингов.** Нужна мультиязычная, у тебя русский. Кандидаты: `bge-m3` (8k контекст, 1024 dim) и `Qwen3-Embedding-0.6B` (ей нужен префикс-инструкция для запросов). Я бы начал с bge-m3. Название модели и размерность записываем в метаданные коллекции: смена модели означает полную переиндексацию, и ядро должно отказаться писать в коллекцию с несовпадающей моделью.
- **Параметры embedder.** `-ngl 0`, `-ub` не меньше размера чанка (иначе llama.cpp отвергнет вход), ограничение `--threads` и `cpus`, чтобы он не воевал за CPU с основным сервером.
- **Падение зависимостей.** LLM лежит (нет сессии): `+rag` отвечает 503 с понятным текстом, MCP-поиск и ингест продолжают работать. Embedder или Qdrant лежат: ядро unhealthy. Стек `restart: unless-stopped` и работает всегда, как мониторинг.
- **Известное ограничение v1:** запрос для поиска строится из последнего сообщения, поэтому follow-up вроде «а подробнее?» ищется плохо. Переписывание запроса по истории добавим позже (оно стоит генерации на 27B, поэтому не по умолчанию).
- **Второй этап, не сейчас:** гибридный поиск (BM25 sparse в Qdrant) и reranker. Он отдельным инстансом llama.cpp, поэтому лишний контейнер заводим только если качество поиска упрётся в потолок.
- **Метрики:** `rag-core` и embedder отдают `/metrics`, а Prometheus из старого репо подключается к `ai-net` и скрейпит их по `file_sd`. Опционально.
